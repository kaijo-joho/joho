# 確認記録の保存と正式提出（2026-10-17）

今回追加するのは、学習用の試行・回答を失わずに持ち運ぶ経路と、その本文を正式採点へ渡す経路。学校の課題への配点追加、本番GASへの配置、OAuth・共有設定、保存GSSの構成変更は行わない。公開設定の `cloudConfig.enabled` と `toolsStoreConfig.enabled` は false を維持する。問題配布専用の検証入口とは分ける。今年度のColab、旧grade、HTMLエディタと教材へのリンクは変更しない。

## ブラウザ内の保存

- 確認記録の書込みは、同一originのWeb Locksでタブ間を排他する。別タブの試行・独立した回答は合流し、同じ回答の同時変更は警告して止める。
- キーは `joho.pythoneditor.confirmations.v2`。v2がなければ旧v1を読み、最初の保存で移行する。旧v1は変更・削除しない。JSONファイル形式のjournalはschema1を維持する。
- 更新前から開いているタブは再読み込みする。旧版タブのv1への書込みを、新版が継続して監視・上書きすることはない。必要な旧記録は保存ファイルで保護する。
- Web Locksを使えない、容量不足、保存拒否、破損の場合は成功表示しない。メモリ内の記録を残し、警告する。ファイル保存は進行中の試行/回答書込みを待ってから出力する。
- クラウドから回答を置換する前と、競合を選ぶ前に控えを保存する。控え保存に失敗すれば置換しない。控えは「ブラウザ保存から復元」の一覧からファイルへ書き出せる。自動削除はしない。
- 回答欄の入力中の値は再描画で消さず、まだ「回答を記録」を押していなければ案内する。未記録の回答があるまま正式提出・ファイル保存へ進んで、以前の回答を今回の内容として送ることを防ぐ。

## 生徒別GSSへのクラウド保存

既存のコード下書きと別にjournalを保存する。コード・試行・回答は正式提出を行わずに自動保存できる。接続時と「クラウドから開く」で最新を照合する。

保存用GASは、各RPCで本人、教員発行binding、origin、保存先と世代、保護/非表示の構成を照合し、利用者ごとのUserLockを使う。生徒権限でシートを作成・共有・保護しない。既存schema1のコード保存はそのまま使える。確認記録の拡張が未準備なら、確認記録だけを準備待ちにする。

候補の追加先は同じ個人GSSの `Python確認` と `Python確認受付` の2シート。本文は最大4MiB・1000試行・2000回答を、最大32000文字ずつに分割する。8つの本文バンクと4096件の不変受付を使い、セル上限へ押し込めない。上限に達した場合も勝手に古い記録を消さず止める。長期運用での容量と処理時間は実測が必要。

クライアントは本人・GSS別の送信番号と同じ本文を控え、通信断後は照会して続きから送る。ブラウザの控え保存ができない場合はメモリで保持し、閉じる前のファイル保存を促す。分割ごとのhashと全体hash、本文の形式、試行コードのhashを検査する。読込みはrevisionと5分リースに固定し、途中で別端末が更新しても版を混ぜない。

クラウド保存はコードと確認記録のRPCを1列で送り、同一生徒の処理を重ねない。通常は変更がある場合のみ、最初の未保存変更から10分を目安に送信する。問題/セット切替、手動保存、提出、保存して終了では待機を飛ばし、コードと確認記録の両方を送る。実行停止後のtrial書込を待ち、通信中の追加入力を古い応答で保存済みにしない。通信失敗は間隔を延ばし、認証切れは停止して再接続する。通信・採用確認の時間を含めた保存完了の保証時間ではない。ローカルファイルのJSON保存を生徒の基本操作とし、終了時はその保存先を確認する。

回答は、直前に確認したクラウド内容を基準に三方向で比較する。片側だけの変更は合流し、両側の異なる変更は選択画面を出す。選択前に両方を控えへ残し、試行は両方を保持する。取得中に回答が変わった場合は再比較し、遅い応答で上書きしない。アカウントが変わる場合は、引継ぐ対象を明示して確認する。

RPCの詳細は[保存用GASの手順](../../scripts/tools-store-gas/store/README.md)、教員側の構成準備は[distの手順](../../scripts/tools-store-gas/dist/README.md)。

## 正式提出と★

確認問題は同じ `submit` RPCへ `kind: confirmation-v1` を送る。含めるのは、その問題/版が参照するコード全文、該当コードの試行履歴、この確認問題の回答だけ。学習用のcompleted・passed・scoreは受け付けない。提出上限を超えた場合は履歴を切り捨てず送信を止める。

サーバーは採用済みの問題・確認条件・非公開正答・明示した配点で再判定する。Pythonを再実行する方式ではなく、端末から来た実行記録の真正性を保証するものではない。旧版codeRefsはその旧版の採用snapshotへ結び付ける。現在の配信版へ差し替えない。

正式配点は既存 `runtimeConfig` の任意の `confirmationGrading` に明示する。未設定なら正式採点/提出と★の対象外で、既定の配点は作らない。具体的な5方式の設定は[確認採点仕様](../../scripts/pythoneditor-gas/CONFIRMATION-GRADING.md)。今回、実課題の正本へ設定値は追加していない。

受付時刻はサーバー到着時点。結果・履歴まで保存されて提出済みとなる。再送は同じ不変ID/本文で回復し、締切内の問題ごとの最高点を採用する。確認問題の★は、採用基準で配点が正の条件数を分母とする。別の提出の条件を寄せ集めない。提出後のコード・試行・回答の変更は得点と別に表示する。

1. 教員権限のdistで、明示した検証用保存GSSへ2シートを追加し、保護/非表示を整え、bindingの世代を更新する。既存コードは保持する。
2. 保存用GASへ候補コードを配置し、`TOOLS_STORE_CONFIRMATION_ENABLED`、dist側 `TOOLS_STORE_DIST_CONFIRMATION_ENABLED` と保存接続を検証対象だけに有効化する。
3. 教員が確認した配点を新しい問題/採点版で採用し、専用gradeの候補追加と受付設定を確認する。同じ採用版の本文・基準は書き換えない。
4. Chrome/Safariの学校実機、教員/デモ/生徒の権限、40名の実GAS同時利用、通信断、認証切れ、貸出機復元、再送、締切、旧版、停止を確認してから範囲を広げる。

今回は上記1〜4の実施は保留。停止時はフロントとGASの新フラグを無効にし、今回の静的コミットをrevertできる。巻き戻し前に現在の確認記録をJSONへ保存する。旧版画面はv2キーを読まないが、JSONのjournalは同じschema1なので元ファイルを保護して取り込める。保存済みGSS・ブラウザの記録・控えは削除しない。本番GASは今回未変更なので巻き戻しも不要。
